# PortTunnel 压测报告

> 测试对象：当前工作区源码（`version=dev`，Go 1.21.13）
> 测试日期：2026-11-24
> 测试范围：隧道数据面（长/短连接、并发、大流量、SQL 审计）、管理面 API、配额与审计开关
> 结论摘要：数据面在长连接场景表现优秀（单客户端 2.9 万次/s 小包往返、约 429 MiB/s 单向大流量），审计链路 0 丢弃；**短连接吞吐存在明确上限（约 1.3k–1.8k 次/s/客户端）**，根因是 yamux 流不支持半关闭导致每条连接固定等待 3 秒收尾并占用流配额，详见第 6 节。

> 修复状态（2026-11-24）：第 6.1/6.3/6.4/6.5 项已修复并完成复测，短连接吞吐提升约 2.6 倍且不再触发流配额拒绝，复测数据见第 9 节；6.2 为客户端操作系统端口限制，需按运维建议处理。

## 6. 发现的问题与风险

### 6.1（高）短连接吞吐被“3 秒收尾 + 流配额”双重限制

**现象**：短连接在 24 并发下只能达到约 1,324 次/s；累计约 1.3 万条成功后开始大量报错，服务端日志出现 `客户端并发连接数已达上限 4096`（本轮 5,457 条）。在短连接刚结束时立即发起 500 并发建连，也会因上一个场景的流尚未释放而失败（实测 146/500 被拒）。

**根因**：yamux v0.1.2 的 `*Stream` 没有 `CloseWrite` 方法，只有 `Close`。因此 [handler.go](file:///f:/ops/隧道穿越/internal/server/proxy/handler.go#L299-L337) 中：

- `closeWrite(stream)` 的类型断言失败后直接返回，半关闭（FIN）不会传递给对端；
- 一端结束后，转发协程必须等待另一方向，最多阻塞 3 秒才强制 `closeAll()`；
- 而流配额在 `countedStream.Close()` 时才归还，等于每条短连接占用流槽位约 3 秒。

按默认 `max_streams_per_client=4096` 计算，理论上限约为 `4096 / 3s ≈ 1,365 次/s/客户端`，与实测（1,324–1,834 次/s）吻合。客户端侧 [agent.go](file:///f:/ops/隧道穿越/internal/agent/agent.go#L562-L586) 存在同样问题。

**影响**：数据库短连接、HTTP 短请求等“连接即用即关”的业务吞吐受限；连接审计的结束时间也会被推迟约 3 秒。长连接与并发连接场景不受影响。

**建议**：

1. 将“收尾等待”做成可配置项（例如 `tunnel.half_close_grace`，默认 3s，短连接场景可设 200–500ms），在 `pipe` 与 `handleStream` 中生效；
2. 评估支持半关闭的复用层（fork/升级 yamux，或改用支持 `CloseWrite` 的 smux 等），从根本上消除 3 秒空等；
3. 若短期无法改造，建议在文档中明确“单客户端短连接上限 ≈ `max_streams_per_client` / 3 秒”，需要更高短连接吞吐时通过多客户端分摊或业务侧连接池解决。

### 6.2（中）客户端本地端口 TIME_WAIT 会限制高频短连接

高频短连接时，客户端为每次转发向目标地址新建 TCP 连接并正常关闭，端口进入 TIME_WAIT。本次测试机动态端口范围仅 1,024–15,000（13,977 个）、`TcpTimedWaitDelay=30`，在未限速的短连接冲击下，累计约 0.6–1.3 万次后客户端日志出现：

```
dial tcp 127.0.0.1:18080: connectex: Only one usage of each socket address ... is normally permitted.
```

**建议**：生产优先部署在 Linux（`net.ipv4.tcp_tw_reuse=1`、扩大 `ip_local_port_range`）；短连接业务使用连接池；或在代理层评估连接复用能力。

### 6.3（低）每连接一个 MAC 解析 goroutine

[audit.go](file:///f:/ops/隧道穿越/internal/audit/audit.go#L94-L110) 在每条连接 `StartConn` 时启动 `go w.resolveMAC(...)`。短连接洪峰下会产生大量短生命周期 goroutine，与 Windows 下观察到的线程/内存抖动有关（虽有 60s 缓存）。

**建议**：改为在审计写协程内按需查询，或对同 IP 做去重/采样后再查。

### 6.4（低）代理连接上限检查存在竞态

[handler.go](file:///f:/ops/隧道穿越/internal/server/proxy/handler.go#L175-L189) 先 `Load()` 再 `Add(1)`，高并发下可能瞬时超过 `max_conns` 几条。本次分批建连未复现，但建议改为 CAS（`CompareAndSwap`）或在自增后复核。

### 6.5（提示）缺少运行态诊断入口

服务端没有 pprof / 运行态 goroutine 快照入口，短连接洪峰后的内存与线程驻留只能靠系统工具观察。建议增加仅监听内网、需鉴权的 `pprof` 调试端点。

## 7. 结论与建议

1. **数据面长连接能力充足**：单客户端 3 万次/s 小包往返、2.5 万次/s 4KB 往返、429 MiB/s 单向吞吐，P99 均在 3–5 ms（回环）。
2. **审计链路可靠**：全量连接审计仅增加约 3.5% 开销，2.3 万连接 + 3.2k SQL 语句写入零丢弃；SQL 提取内容正确。
3. **配额与限流按预期生效**：`max_conns`、`max_streams` 均精确拦截。
4. **短连接是当前主要短板**：约 1.3k–1.8k 次/s/客户端，根因明确（yamux 无半关闭 + 固定 3 秒收尾 + 流配额占用），建议优先改造收尾逻辑。
5. **Windows 仅适合功能验证**：本地端口与线程/内存表现明显受限，生产环境请以 Linux 复测为准，并补充 pprof 与内存监控。
