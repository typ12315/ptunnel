## 3. 关键选型说明

### 3.1 Web 框架：Gin（备选 chi / Echo / 标准库）

- 项目会同时承载「Web 静态资源 + REST API + 需要精细控制的 TLS 监听」，Gin 提供成熟的路由分组、中间件、`ShouldBindJSON`，开发效率最高。
- 缺点：非标准库。若追求极简可换 `go-chi/chi`（接近标准库、中间件同样丰富），代码改造量约 1 人日。
- 隧道端口上，业务数据**不经过** HTTP 栈：TLS 握手后按 ALPN 分流，`h2` 直接交给 yamux；仅客户端证书注册/续期走 HTTP。为保证安全边界，隧道端口使用独立的最小路由（只挂载 `/api/enroll`、`/api/client/cert/renew` 与 `/healthz`），管理面接口只监听 `admin_addr`。

### 3.2 多路复用：yamux（备选 QUIC / gRPC / 自研）

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **yamux over TLS/TCP** | 成熟稳定、单连接多流、流控内置、API 简单 | 单连接故障影响该客户端全部代理；无 0-RTT | **采用** |
| QUIC (quic-go) | 抗丢包、连接迁移、多流 | 复杂度高（UDP 受限环境）、调试与运维成本高 | 二期可选 |
| gRPC 双向流 | 编解码规范 | 不适合裸 TCP 字节透传（需自建帧层），额外依赖 | 不采用 |
| 自研帧协议 | 完全可控 | 流控/半关闭/背压全部自实现，bug 风险高 | 不采用 |

使用要点：

- 关闭 yamux 自带 keepalive，改由控制流应用层 Ping/Pong（避免误杀长空闲业务连接）。
- 配置 `MaxStreamWindowSize` 按内存预算调整（默认 256 KB → 视并发调至 512 KB）。
- 服务端开启 `AcceptBacklog` 默认值即可，单客户端流上限通过服务端连接计数中间件控制。

### 3.3 数据库：SQLite（modernc，无 CGO）

- 满足单机、低运维、单文件备份的诉求；写入以配置变更与 5 分钟统计为主，压力极小。
- 选 `modernc.org/sqlite` 而非 `mattn/go-sqlite3`：后者需 CGO，Windows 交叉编译 Linux 会引入工具链问题，直接排除。
- 参数：`?_pragma=journal_mode(WAL)&_pragma=busy_timeout(5000)&_pragma=foreign_keys(ON)&_pragma=synchronous(NORMAL)`。
- 仓储层直接使用 `database/sql`（`internal/store` 下按实体拆分文件），查询均为显式 SQL；如后期需要多节点可再抽象接口替换 PostgreSQL。
- 迁移：`//go:embed migrations/*.sql` + `schema_migrations` 表按文件名顺序执行，避免引入额外迁移框架。

### 3.4 配置：yaml.v3 + 标准库 flag

- 服务端/客户端各一个 YAML 文件，`gopkg.in/yaml.v3` 解析；关键项支持环境变量覆盖（`PTUNNEL_ADMIN_USER`、`PTUNNEL_ADMIN_PASSWORD`）。
- 自定义 `Duration` 类型支持 `15s` / `5m` 写法；默认值在 `config.DefaultServer/DefaultClient` 中集中定义。
- 校验在 `internal/config` 的 `Validate` 中完成（监听地址、端口范围、审计模式），启动即 fail fast。

### 3.5 前端：Vue3 + Vite + Element Plus（内嵌）

- 管理后台以表格、表单、图表为主，Element Plus 覆盖度高，开发成本最低。
- 构建产物输出到 `internal/server/web/dist`，通过 `//go:embed all:dist` 嵌入二进制；Gin `NoRoute` fallback 到 `index.html` 支持前端 history 路由。
- 前后端契约：直接使用总体设计第 8 节的 REST API；规模较小，前端使用 JS（未引入 TypeScript/OpenAPI 生成器）。
- 备选（若不希望引入 Node 构建）：Go `html/template` + Alpine.js + HTMX + 预编译 Tailwind CSS；交互复杂度会上升，故不作首选。

### 3.6 认证与会话

- 管理面：`POST /api/auth/login` 校验 Argon2id → 签发 HMAC-SHA256 签名 Cookie（含 `uid`、`exp`、`jti`），服务端保存 `jti` 白名单以支持注销/强制下线；写操作校验 CSRF Token（双提交 Cookie）。
- 客户端面：不使用口令，完全依赖 mTLS 证书；证书 CN 即身份。
- 不改用 JWT 库：需求简单，标准库 `crypto/hmac` + `base64` 足够，少一个依赖面。

### 3.7 TLS / PKI

- 全部使用标准库：`x509.CreateCertificate`（CA 与客户端证书）、`x509.CreateCertificateRequest`（客户端 CSR）、`tls.Config{ClientAuth: RequireAndVerifyClientCert, VerifyPeerCertificate: 吊销校验}`。
- ALPN 固定 `h2`（对外表现为普通 HTTP/2，避免抓包识别为隧道；同时兼容旧值 `ptunnel/1` 以便滚动升级），握手后校验 `ConnectionState().NegotiatedProtocol`，防止误连到管理端口。
- 不引入第三方 PKI 库，避免 CA 私钥被框架以非预期方式落地。

### 3.8 连接审计的实现方式

| 关注点 | 做法 |
| --- | --- |
| 采集点 | 端口监听器 `Accept` 成功后（含被拒绝连接）生成 `conn_id` 并打快照；转发结束时回填结束信息 |
| 计数 | 自实现 `countingConn` 包装 `net.Conn`，`io.Copy` 返回后读取即可，无需额外解析 |
| 写入 | 内存有界队列（cap 10000）+ 单写协程，每 500 ms 或 200 条触发一次事务批量 upsert；队列满用非阻塞 `select` 丢弃并计数 |
| 悬挂恢复 | 启动时将 `ended_at IS NULL` 的历史行标记 `close_reason='unclean'`，保证「活跃连接」准确 |
| MAC 查询 | `internal/audit/mac`：Linux 读 `/proc/net/arp`；Windows 调用 `arp -a <ip>` 解析（无需 CGO）；结果缓存 60 s，异步执行不阻塞 Accept |
| 查询 | 列表走覆盖索引（`started_at` / `client_id+started_at` / `remote_port+started_at` / `src_ip+started_at`），分页 limit 100；导出 CSV 流式写出（`encoding/csv` + `http.Flusher`） |
| 清理 | 每日 03:00 定时任务，分批 5000 行 `DELETE ... WHERE started_at < ?`，避免长事务锁库 |

明确边界：MAC 只能在与服务端同二层时取得，跨网段为 NULL；实现上不重试、不阻塞，避免为审计牺牲转发性能。

## 4. 依赖清单（go.mod 预期）

```text
module ptunnel
go 1.21

require (
    github.com/gin-gonic/gin   v1.9.1
    github.com/google/uuid     v1.6.0
    github.com/hashicorp/yamux v0.1.2
    golang.org/x/crypto        v0.24.0
    gopkg.in/yaml.v3           v3.0.1
    modernc.org/sqlite         v1.29.10
)
```

直接依赖只有 6 个，其余均为 Gin 与 modernc/sqlite 的传递依赖。

依赖原则：

- 能用标准库就不引第三方（TLS/PKI、日志、哈希、HTTP 客户端、CSV、指标文本输出均用标准库）。
- 所有依赖 `go mod tidy` 后提交 `go.sum`；CI 执行 `go mod verify`。

## 5. 工程规范

### 5.1 目录与命名

见总体设计第 13 节；包名小写单词，不用下划线；对外暴露最小接口集，实现返回具体类型。

### 5.2 代码质量

```text
make lint    # golangci-lint run ./...（errcheck, govet, staticcheck, revive, gosec）
make fmt     # gofumpt -l -w .
make test    # go test -race -count=1 ./...
make build   # 交叉编译 linux/amd64, linux/arm64, windows/amd64
```

- 所有 `error` 必须被处理或显式 `_ =` 并注释原因；`gosec` 纳入 CI（重点检查 TLS 配置与文件权限）。
- 并发代码必须通过 `-race`；隧道读写使用 `io.Copy` + `net.TCPConn.CloseWrite`。

### 5.3 测试策略

| 层级 | 内容 | 工具 |
| --- | --- | --- |
| 单元 | 配置合并策略、流头编解码、CIDR 匹配、端口注册冲突、审计批量写（含队列满丢弃） | `testing` |
| 集成 | 进程内起 server + agent，回环验证 1KB/10MB 传输、半关闭、超时、白名单拒绝、conn_logs 字段完整性（含 rejected 记录） | `net.Pipe` + 临时端口 + 临时 SQLite |
| 端到端 | 编译真实二进制，脚本启动 server/client，用 `curl`/`nc` 验证访问并在 Web/API 查询连接审计 | PowerShell + bash 脚本 |
| 压测 | 并发 1000/5000 连接、吞吐基准、审计写入不阻塞转发的验证（`go test -bench`） | 内置 benchmark |
| 故障注入 | kill 客户端 / 断开隧道 / 占用端口 / kill -9 服务端后校验 `unclean` 收尾 | 脚本 |

### 5.4 配置与密钥

- 私钥/证书文件权限 0600，目录 0700；启动时检查权限并在日志告警。
- 服务端 CA 私钥支持通过 `PTUNNEL_CA_KEY_PASSPHRASE` 环境变量加密存储（二期，可选）。

## 6. 构建与交付

```makefile
build:
	go build -trimpath -ldflags "-s -w -X main.version=$(VERSION)" -o bin/ptunnel-server ./cmd/ptunnel-server
	go build -trimpath -ldflags "-s -w -X main.version=$(VERSION)" -o bin/ptunnel-client ./cmd/ptunnel-client

web:
	npm --prefix web ci && npm --prefix web run build   # 产出 web/dist → embed
```

- `goreleaser` 输出：`linux_amd64/arm64`、`windows_amd64` 归档 + `checksums.txt`。
- Docker：多阶段构建（`node` 构建前端 → `golang` 编译 → `gcr.io/distroless/static` 运行），镜像 < 30 MB。
- systemd 单元示例（服务端）：`Restart=always`、`LimitNOFILE=65535`、`NoNewPrivileges=true`、`ProtectSystem=strict`、`ReadWritePaths=/var/lib/ptunnel`。

## 7. 版本与兼容性策略

| 项 | 策略 |
| --- | --- |
| Go 版本 | 固定 minor（1.24.x），`go.mod` 声明 `go 1.24`，CI 使用相同版本 |
| 控制协议 | `hello` 携带 `version`；服务端兼容 N-1 小版本；破坏性变更时提升 ALPN 为 `ptunnel/2` |

## 8. 明确不引入的技术

| 技术 | 不采用原因 |
| --- | --- |
| gRPC / protobuf | 裸 TCP 透传场景收益低，增加工具链与调试成本 |
| GORM | 表结构简单，隐式 SQL 与迁移行为不利于性能与可控性 |
| Redis / 消息队列 | 单机规模无需外部中间件，违背「单二进制」目标 |
| JWT 库 | 自签 Cookie 已够用，减少依赖与误用（如无撤销机制） |
| React / Next.js | 管理后台无 SSR 需求，Vue 3 + Vite 更轻 |
| Nginx 前置 | 服务端自身处理 TLS 与静态资源，减少部署环节 |
